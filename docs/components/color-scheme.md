# Victorian Gothic Color Scheme Architecture

## 1. Purpose and Scope

`VictorianGothic.colors` is the canonical KDE color-scheme artifact for
MidnightOnyx Gothic.

It maps the project's visual color vocabulary onto KDE semantic color
roles using KDE's standard `.colors` format.

The component is responsible for semantic color configuration. It is not
responsible for widget geometry, Plasma component layout, wallpaper
rendering, icons, fonts, or application-specific styling that does not
consume KDE color roles.

## 2. Architecture Constraints

The component must:

-   Remain a valid KDE color-scheme file.
-   Use standard KDE semantic color groups.
-   Be installable without privileged access for ordinary user use.
-   Remain usable independently of other MidnightOnyx components.
-   Avoid machine-specific configuration.
-   Treat the repository file as canonical.

## 3. Technical Context

``` text
VictorianGothic.colors
        |
        v
KDE color-scheme discovery
        |
        +-----------------------+
        |                       |
        v                       v
plasma-apply-colorscheme   KDE/Qt consumers
        |
        v
kdeglobals
```

KDE expands the selected `.colors` scheme into semantic color groups in
`kdeglobals`.

## 4. Building Blocks

### Canonical asset

``` text
assets/color-schemes/VictorianGothic.colors
```

This is the source of truth.

### KDE semantic groups

The scheme defines KDE color groups including:

-   `Colors:Button`
-   `Colors:Complementary`
-   `Colors:Header`
-   `Colors:Selection`
-   `Colors:Tooltip`
-   `Colors:View`
-   `Colors:Window`
-   window-manager colors
-   inactive and disabled color effects

### KDE application tooling

`plasma-apply-colorscheme` is the preferred KDE mechanism for applying
the scheme.

Development should not duplicate KDE's color-scheme expansion logic with
a custom collection of `kwriteconfig6` commands.

## 5. Runtime and Configuration Behavior

Applying the scheme through KDE produces an expanded `kdeglobals`
representation containing the semantic groups plus:

``` text
ColorScheme=VictorianGothic
ColorSchemeHash=<KDE-generated hash>
```

Development experiments established that KDE produces the same
color-scheme hash for the same accepted scheme when applied in separate
temporary user contexts.

The hash is generated by KDE and should not be independently implemented
by MidnightOnyx.

## 6. Deployment

### Per-user

The standard user-level deployment location is:

``` text
~/.local/share/color-schemes/VictorianGothic.colors
```

### System-wide

A system-wide deployment may place the asset under:

``` text
/usr/share/color-schemes/VictorianGothic.colors
```

System-wide installation is useful when a consumer outside the normal
user's XDG data path must discover the scheme.

Packaging should install from the canonical repository asset.

## 7. Plasma Login Manager Findings

The color scheme can be discovered and applied in the `plasmalogin`
account context using KDE's own color-scheme tooling.

The resulting `kdeglobals` remains owned by the `plasmalogin` account
and the configuration persists across reboot.

However, color configuration alone does not redefine the geometry or
composition of PLM's Breeze-based greeter controls.

PLM and Breeze consume semantic colors, but visible control geometry and
layout are governed by upstream QML components.

The color scheme should therefore be treated as one layer of the
appearance stack rather than a complete login-screen theme.

## 8. Quality Requirements

### Compatibility

The scheme should remain valid against the KDE color-scheme format used
by targeted Plasma releases.

### Modularity

Users must be able to install and use the color scheme without
installing unrelated MidnightOnyx components.

### Determinism

The repository asset must be the only manually maintained source of
color-role values.

### Reversibility

Removing the installed asset must not require editing the canonical
source or upstream package files.

## 9. Testing Strategy

Validation should include:

-   File-format and required-group inspection.
-   KDE discovery through `plasma-apply-colorscheme --list-schemes`.
-   Application in an isolated temporary configuration directory.
-   Verification of generated `ColorScheme` identity.
-   Visual inspection in representative KDE/Qt applications.
-   Compatibility checks against targeted Plasma releases.

## 10. Risks and Open Issues

-   Upstream semantic roles may evolve.
-   Individual applications may not consume KDE color roles
    consistently.
-   A color scheme cannot by itself provide complete visual theming for
    Plasma or PLM.
